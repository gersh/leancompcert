# Helfgott Prop. 12.2.4: the per-`q` row, measured

`LeanCompCert/Ports/Prop1224Row.lean`, emitted through
`bench/Prop1224RowEmit.lean` and checked against `bench/ref_p1224.c` by
`bench/p1224_row_check.sh`.  This box: 20 cores, `gcc -O2`, `ccomp` 3.17 `-O`.
Other jobs were running throughout, so **user** CPU time is quoted rather than
wall, and the spread between repeats is given where it matters.

## Agreement with the oracle

The artifact prints, out of its per-row planes, exactly the eleven columns
`ref_p1224.c`'s `row` mode prints — `q φ ω L_lo L_hi f₁ ⌊2^E φ/q⌋ const κ* ϖ λ` —
and a `SUM` line in the same ten fields.  One differing digit anywhere fails
the check.  `ref_p1224.c` was written from the mathematics by someone who had
never seen this encoding; it is not a transliteration of the register machine.

| range | rows | slots | `smallQ` | gcc `-O2` | `ccomp -O` |
| --- | ---: | ---: | --- | --- | --- |
| `[1, 257)` | 256 | 7 | yes | rows + SUM identical | identical |
| `[129000, 133096)` — straddles `2^17` | 4 096 | 7 | yes | identical | identical |
| `[10⁶, 10⁶+4096)` | 4 096 | 6 | no | identical | identical |
| `[3·10⁹, 3·10⁹+16384)`, table of the full `3.3·10⁹` sweep | 16 384 | 6 | no | identical | identical |
| `[3·10⁹, 3·10⁹+65536)`, same table | 65 536 | 6 | no | `SUM` identical | — |

`RET 0` on every run: no failed square-root certification
(`ExpFixed.expOK`'s two comparisons, checked on every one of the row's
`5 · 24 = 120` roots), no exhausted mark budget, no violated row guard.  The
`ccomp` and `gcc` binaries of the same translation unit print byte-identical
output.

A third implementation — exact-integer Python, written from the formulas —
agrees with `ref_p1224.c` on `[1, 12)`, `[131068, 131075)` and
`[3·10⁹, 3·10⁹+4)`; it exists to localise a disagreement, and was not needed
after the first one.

## The one bug the oracle caught

`lnLo`'s `logFix S n * l2lo32 >>> lnShift` parses in Lean as
`logFix · (l2lo32 >>> lnShift)`, because `>>>` binds tighter than `*`.  Every
`L(q)` and every packed table entry was then wrong, and the entry's third field
overflowed `2⁶⁴` and was truncated by the C compiler.  The artifact's own
guards cannot see this — the numbers are consistent, just not the right ones —
and it was found by the first row-by-row comparison.  `entryOK`/`tableOK` now
refuse to emit a translation unit whose packed fields do not round-trip.

## Corrected compact-stream coefficient

The row's fourth retained oracle column is `f1Hi`, but `CellCfg` consumes
`afHi = ceil(kAHi*f1Hi/2^E)`.  An earlier smoke driver passed `f1Hi` directly,
which made the negative envelope too small.  The compact row program now
performs that conversion itself with a multiply, shift, mask, nonzero test,
and add, and stores `afHi` as its fourth field.  For the smoke row `q=30`,
this changes the cell input from `45879730` to `209640114`.

`Prop1224RowCompactSemantics.afHiBlock_run` proves the exact five-instruction
natural-number result, and
`Prop1224RowFixedPointSoundness.afHiBlock_output_enclosed` proves that the
emitted word is an upper enclosure of `omega* * 7.284 * f1(q)`.  Both theorem
closures contain only foundational axioms.  The corrected 32-row/13-cell
positive and fail-safe smoke, including both negative controls, passes.

## Cost

Production configuration: mark table for `tableHi = 3.3·10⁹` — the `5 823`
primes below `⌊√(3.3·10⁹)⌋ = 57 445`, two cells each — six slots of `S = 24`
squaring rounds, `segLen = 16384`.

| `expUnroll` | body | iterations/row | instructions/row | `q ≈ 3·10⁹`, gcc |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 869 | 147.1 | 127 868 | — |
| 4 | 1 625 | 40.7 | 66 124 | **9.6 µs** (0.63 s / 65 536) |
| 8 | 2 633 | 22.7 | 59 800 | 12.8 µs (0.21 s / 16 384) |
| 24 | 6 665 | 9.1 | 60 949 | — |

`expUnroll` is the module's main cost knob and it is not about the
exponential: every phase's instructions run on every iteration, so the
segmented sieve, the slot muxes and the row finish's ten divisions are paid
once per iteration whether or not that iteration wants them.  Fewer, fatter
iterations is the whole trade, and it bottoms out around `4`–`8`.

Compiler ratio, on identical translation units:

| artifact | gcc | ccomp | ratio |
| --- | ---: | ---: | ---: |
| `q ≈ 3·10⁹`, `expUnroll = 8`, 16 384 rows | 0.21 s | 0.26 s | 1.24 |
| `q ≈ 10⁶`, `expUnroll = 4`, 262 144 rows | 2.57 s | 4.02 s | 1.56 |

so **`ccomp` costs `1.2`–`1.6×` gcc**; at `expUnroll = 4` and `q ≈ 3·10⁹` that
is `12`–`15 µs` per row.

### CompCert's compile cost is the practical wall

`ccomp -O` on the production translation unit — `2.2 MB`, an init block of
`11 648` literal stores and a `2 633`-instruction loop body over `546` locals —
took **38 minutes** (`4m28` user, `9m18` sys) and `6.5 GB` resident.  gcc
compiles the same file in seconds.  This is the same hazard the mark table has
run into before (`27 421` literal entries overflowed `ccomp`'s stack); `11 648`
does not overflow it, but it is expensive.  A production chain compiles one
artifact per slice, so this is paid once per slice, not once per row — but it
is a real cost and it caps how much of the table can be emit-time.

## Against the MPFR campaign

| phase | work | cost |
| --- | ---: | ---: |
| `q` rows, `expUnroll = 4`, ccomp | `3.389·10⁹` | `≈ 12` core-hours (`9.0` under gcc) |
| `(q,k)` cells, `1.2·10⁸` `r`-steps, ccomp | measured earlier | `0.03` core-hours |
| **total** | | **`≈ 12` core-hours** |

against the `105–640` core-hours the MPFR campaign budgets — a factor of
`9` to `53`.  The earlier projection in `docs/prop-12-2-4-port-projection.md`
said `5.6`; the row phase came in at about twice that, for two reasons that
the projection did not model: the row needs **five** exponentials, not four
(the large prime's `p^{1/3}` and `p^{2/3}` are both wanted, and the projection
counted the simplified `1 + p^{−2/3}` bound that `ref_p1224.c` does not use),
and the per-iteration cost of the sieve, the muxes and the ten divisions is
paid on every one of the `40` iterations a row costs, not once.

**Nothing has been run at scale.**  These are measurements of `2·10⁵`
production-parameter rows, extrapolated linearly over `3.389·10⁹`.
The compiled `afHi` conversion adds five division-free instructions to the
1,625-instruction compact body (about `0.31%`), so it does not change the
rounded `12` core-hour projection.  Using the observed `12–15 us` CompCert
range gives `11.3–14.1` core-hours for the positive row execution.  CompCert
compilation remains a separate approximately 38-minute cost per production
translation unit; the fail-safe audit execution still needs a representative
production-parameter timing before it can be included more tightly than as a
separate multiplicative overhead.
